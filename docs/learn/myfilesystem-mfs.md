# MyFileSystem (MFS) の設計と実装

MFS は MyKernel の最小ファイルシステム。SSD ブロックデバイスの上に、FAT 的な
ブロックチェインで可変長ファイルを載せる。実 FS の主要概念（inode 的なエントリ表、
ブロックビットマップ、FAT チェイン、オープンファイルテーブル、バッファキャッシュ、
スーパーブロックのマジック）を最小構成で一通り含む教材でもある。

コード: `system/MyKernel/src/libs/fs.mln`
下位レイヤ: `system/MyKernel/src/libs/ssd.mln`（ドライバ）、
`runtime/MyEmulator/src/machine/ssd.rs`（デバイス）

---

## 前提：SSD はブロック単位でしか読み書きできない

SSD デバイスは 65536 バイト（= 1 ブロック）を最小単位として転送する。1 バイトだけ
読む/書くことはできない。一方 FS がやりたいのは「エントリの 20 バイト目を書く」
「ビットマップの 3 ビット目を立てる」といった細かいバイト操作。

この粒度差を埋めるのが **read-modify-write** パターン。MFS のあらゆる操作はこの形を取る:

```
ssd.read_block(n, g_buf);   // ① ブロック n を作業バッファ g_buf(64KB) に載せる
... g_buf の中をバイト単位で編集 ...   // ② modify
ssd.write_block(n, g_buf);  // ③ 書き戻す
```

`g_buf` は実 OS の「バッファキャッシュ / ページキャッシュ」の最小形。

## ディスクレイアウト（65536B ブロック × 16384 = 1GB）

| ブロック | 用途 |
|----------|------|
| 0 | スーパーブロック（マジック・バージョン・max_files） |
| 1 | ファイルエントリ表（2048 エントリ × 32 バイト） |
| 2 | ブロック割当ビットマップ（16384 ビット = 2048 バイト） |
| 3..16383 | データブロック |

### ① スーパーブロック（block 0）

「このディスクは MFS だ」という目印と設定。

```
off 0: MAGIC = 0x4D465331 ('MFS1')  ← あれば既存FS、なければ未フォーマット
off 4: VERSION
off 8: MAX_FILES
```

`init()` が block 0 を読み、マジックが一致しなければ `format()` を呼ぶ（自動フォーマット）。
これが「初回は作る、2 回目以降は残す」= 永続化判定の正体。

### ② エントリ表（block 1）= ファイルの目録

1 ファイル = 32 バイトのエントリ。1 ブロックに 2048 個入る。

```
off 0..16 : ファイル名（null 終端、最大 15 文字）
off 16    : first_block  ← 0 なら空きスロット、非 0 なら先頭データブロック番号
off 20    : file_size（バイト数）
off 24,28 : 予約
```

`first_block == 0` が「空きスロット」の判定を兼ねる（別途 used フラグを持たない）。

### ③ ビットマップ（block 2）= ブロックの使用状況

全 16384 ブロックの空き/使用を 1 ビットずつ記録。

```
bit b が 1 → ブロック b は使用中
bit b が 0 → ブロック b は空き
```

`alloc_block()` は空きビットを探して立て、`free_block()` はビットを落とす。
16384 ビット = 2048 バイトなので 1 ブロックに収まる。

### ④ データブロック（block 3〜）= 実データ

各データブロックの先頭 4 バイトが「次への矢印」。これで連結リスト（FAT チェイン）を作る。

```
bytes[0..4]      : next_block（次ブロック番号、0 = チェイン終端）
bytes[4..65536]  : payload（実データ 65532 バイト = PAYLOAD）
```

1 ブロック固定サイズなのに任意長ファイルを持てるのは、この next ポインタで
数珠つなぎにするから。

## メモリ側の構造（RAM、永続しない）

### g_fd_table — オープンファイルテーブル

```c
typedef struct {
    i32 entry_idx;   // -1 = 空きスロット
    i32 offset;      // 現在の読み書き位置（カーソル）
    i32 first_block;
    i32 file_size;
} OpenFile;
OpenFile g_fd_table[8];  // 同時に開けるのは最大 FD_MAX(=8) 個
```

ディスクの目録②のキャッシュ + カーソル。`open` で作られ、`close` で解放。
Linux の `ulimit -n`（プロセスが同時に持てる fd 数）と同じ思想の上限が FD_MAX。

### g_buf — 作業バッファ

1 ブロック（65536B）を載せて編集する領域。`init` で `heap.alloc(BLOCK_SIZE)`。

## 各操作の流れ

合言葉: **ディスクは g_buf 経由でしか触らない**。

### create(name)

```
1. find_entry_by_name → 同名があればエラー（重複禁止）
2. find_free_entry    → 空きエントリ番号（first_block==0）を得る
3. alloc_block        → 空きデータブロックを 1 つ確保（ビットマップを更新）
4. そのブロックを空(next=0)で初期化して書く
5. エントリに 名前・first_block・size=0 を書き、エントリ表を書き戻す
6. open(name) して fd を返す
```

### open(name)

```
1. find_entry_by_name でディスクの目録からエントリ番号を探す
2. find_free_fd で g_fd_table の空きスロットを探す
3. エントリ情報(first_block, file_size)を g_fd_table[fd] にコピー、offset=0
4. fd（テーブル添字）を返す
```

目録②の情報を RAM の g_fd_table にロードし、カーソルを 0 にするのが本質。

### write(fd, buf, size) — 追記

```
1. first_block からチェインを辿り、最後のブロック(next==0)へ
2. 空き位置(in_block)から buf のバイトを 1 個ずつ payload に詰める
3. ブロックが満杯(PAYLOAD)になったら:
     alloc_block → 今のブロックの next に新番号を書く → 新ブロックへ移る
4. 書き終えたら finish_write で file_size を更新
```

`buf` は呼び出し側の素のバイト配列で `ram_byte(buf + written)` で 1 バイトずつ読む。
（この「1 アドレス 1 バイト」規約を、fs 内部の g_buf ワードアクセスと混同すると化ける。
 実際に初期実装で `'hi fs'` が `' i  '` に化けるバグを踏んだ。）

境界の注意: `file_size % PAYLOAD == 0` かつ `file_size > 0` のとき最後のブロックは
ちょうど満杯なので、追記前に新ブロックを 1 つ確保しておく必要がある。

### read(fd, buf, size)

```
1. offset から「何ブロック目か(offset/PAYLOAD)」を計算し、チェインをそこまでスキップ
2. payload を 1 バイトずつ buf にコピー(set_ram_byte)
3. ブロック末尾で next へ進む。file_size に達したら終了
4. offset を進め、読んだバイト数を返す
```

write の逆。offset というカーソルで位置を管理し、チェインを辿る。

### remove(name)

エントリのチェインを辿って各ブロックを `free_block`（ビットマップを落とす）し、
エントリを空(first_block=0)にして書き戻す。

## 全体を貫く 3 つの原則

1. **すべてブロック単位の read-modify-write**
   バイト操作したくても SSD はブロック単位。g_buf に載せて編集して書き戻す。
   = OS のバッファキャッシュの最小形。

2. **メタ情報もデータも全部ディスク上**
   目録②・ビットマップ③・データ④が全部ディスクにあるので再起動しても残る。
   RAM 側(g_fd_table)は「今開いているものの一時状態」だけ。これで永続化が成立。

3. **チェイン（連結リスト）で可変長を実現**
   1 ブロック固定なのに任意長を持てるのは next_block で数珠つなぎにするから。
   これは実 FS の FAT と同じ。

## 実 OS/FS との対応

| MFS | 実 OS/FS の概念 |
|-----|-----------------|
| エントリ表② | ディレクトリ / inode テーブル |
| ビットマップ③ | ブロックビットマップ（ext2 等） |
| next_block チェイン | FAT（File Allocation Table） |
| g_fd_table | プロセスのオープンファイルテーブル |
| offset | ファイルポジション（lseek が動かす） |
| FD_MAX | ulimit -n（同時オープン数上限） |
| g_buf | バッファキャッシュ / ページキャッシュ |
| MAGIC | スーパーブロックのマジック（全 FS 共通の慣習） |

---

## 現状の弱点（今後の学び/改善の種）

- **追記専用**: write はチェイン末尾への append のみ。offset 指定の
  ランダムライト（上書き）は未対応。
- **フラット**: ディレクトリ階層なし。全ファイルが 1 つのエントリ表に並ぶ。
- **エントリ走査**: find 系は 1 ブロックに全エントリがある前提で「1 回読んで
  メモリ上を走査」に最適化済み。テーブルが複数ブロックに増えたら要再設計。
- **断片化・耐障害性**: alloc は先頭優先の単純割当。書き込み途中のクラッシュに
  対するジャーナリング等はない。
- **1GB を毎回フォーマット走査しない工夫**: format はメタ 3 ブロックだけ書くので軽いが、
  ディスクを大きくするとビットマップ/エントリ設計の見直しが要る。

これらは実 FS が「エクステント」「ジャーナル」「B-tree ディレクトリ」などで
解決している。MFS はそれらの出発点として最小形を提供している。
