# メモリの配置：アドレスの作り方、物理メモリ、プロセスの空間

**Status:** 実装済み（2026-11-10）。

**Scope:** 命令がアドレスを作る方法、カーネルイメージの読み込み、物理メモリの分け方、
プロセスの仮想アドレス空間

---

## 0. 一言で

アドレスは 2 命令で 32 ビットを作るので、カーネルもアプリもどこにでも置ける。
カーネルは RAM 全体を恒等マップで持ち、アプリは 1 GB から上を使う。
物理ページはカーネルヒープとは別の場所から 1 ページずつ配る。

## 1. アドレスの作り方

`movi` の即値は 21 ビットなので、1 命令では 2 MB 未満の値しか作れない。ジャンプと `call` は
PC 相対で ±32 MB 届くので、制約になるのはアドレスを値として読む場合（グローバル変数、
文字列、関数ポインタ）だけである。

`lui rX, imm`（`rX = imm << 11`）と `addis rX, imm` の 2 命令で 32 ビットを作る。
`addis` に渡す下位 11 ビット（0〜2047）は、21 ビットの符号付き即値として負にならない。

| 書き方 | 出力 | 再配置 |
| --- | --- | --- |
| `movi rX, label`（`mov rX, label` も） | `lui rX` + `addis rX` | `RELOC_HI21`（address >> 11）、`RELOC_LO11`（address & 0x7FF） |
| `movi rX, 数` | `movi rX`（1 命令） | なし |
| `.word label` | 32 ビットの語 | `RELOC_WORD32` |

アセンブラがこの展開をするので、コンパイラの出力も手書きのアセンブリも変えていない。
代わりにアドレスを読む箇所は 1 命令長くなる（カーネルで約 5,000 箇所、約 20 KB）。
`RELOC_ABSOLUTE`（21 ビットの `movi`）はリンカに残っていて、収まらないアドレスを拒む。

## 2. カーネルイメージの読み込み

ファームウェアは SSD のブロック 16000 から、カーネルを物理 0x100000 に読み込む。

1. 最初の 64 KB ブロックを読む。
2. イメージの 2 語目にあるイメージの終わりのアドレス（`system/MyOS/src/boot/stub.masm` の
   `.word _end`）を読み、必要なブロック数を求める。
3. 残りのブロックを読み、0x100000 へ飛ぶ。

上限は 64 ブロック（4 MB）。`tools/mkfs.py` はそれより大きいイメージを拒む。

## 3. 物理メモリ（RAM 512 MB）

| 範囲 | 中身 |
| --- | --- |
| `0x0000_0000 ..` | ファームウェアが使う低位の領域 |
| `0x0010_0000 .. _end` | カーネルイメージ（MyKernel と MyOS） |
| `_end .. +8 MB` | カーネルヒープ（`heap.mln`）：カーネルのオブジェクト、カーネルスタック |
| `ヒープの終わり .. 0x1F00_0000` | 物理ページの置き場（`frames.mln`）：ページ表とプロセスのページすべて |
| `0x1F00_0000 .. 0x2000_0000` | 起動時のスタックの領域 |

`frames.mln` は 4 KiB ずつ配る。空いたページは自分の先頭の語で次の空きページを指すので、
管理用のメモリはいらない。まだ一度も配っていないページは、先頭から順に取る。以前は
ページをカーネルヒープから取り、境界合わせのため 1 ページに 8 KiB を使っていた。

カーネルは RAM 全体を恒等マップで持つ（ページ表 128 枚、512 KiB）。ページ表に配ったページを
書き、プロセスのページに実行ファイルの中身を写すには、そのページに物理アドレスで届く
必要があるからである。表は 1 枚ずつまとめて書く（`mmu.map_identity_tables`）。

| 範囲 | 権限 |
| --- | --- |
| `0 .. 16 MB`（イメージとヒープ） | 読み書き実行、カーネルのみ |
| `16 MB .. 0x1F00_0000`（物理ページ） | 読み書き、カーネルのみ |
| 起動時のスタック、MMIO、VRAM | 読み書き、カーネルのみ |

## 4. プロセスの仮想アドレス空間

1 GB より下はカーネルの恒等マップで、どのプロセスもカーネルと同じページ表を共有する。
プロセスのページはその上に置く。

| 範囲 | 中身 |
| --- | --- |
| `0x0000_0000 .. 0x3FFF_FFFF` | カーネル（共有、ユーザーモードからは触れない） |
| `0x4000_0000 ..` | プログラムのテキストとデータ（`qa/runners/build_user_apps.py` がここにリンクする） |
| `0x4100_0000 ..` | ヒープ（`sys_sbrk` で上へ伸びる） |
| `0x7F00_0000 .. 0x7FFF_FFFF` | スレッドのスタック（2 MB の枠が 8 つ、`docs/design/threads.md` §9） |

`mmu.map_page` は、ユーザーのページをカーネルのページ表に置こうとすると
`MmuError::KernelRange` を返す。置けば、表を共有する全プロセスに見えてしまうからである。
以前はアプリを 2 MB 未満（0x20000）にリンクし、プロセスごとに 0 番地台のページ表を
複製していたが、どちらも不要になった。

## 5. 決まっていないこと

- **小さなアドレスの 1 命令化。** 2 MB 未満のアドレスは `movi` 1 命令で足りるが、
  アセンブル時には最終アドレスが分からないので、今は常に 2 命令にしている。
- **大きな定数。** コンパイラは 21 ビットに収まらない定数をデータ領域の語から読む。
  `lui` + `addis` にすればメモリを読まずに済む。
- **カーネルヒープの大きさ。** 8 MB のまま。カーネルスタック（スレッドごとに 16 KiB）も
  ここから取る。
