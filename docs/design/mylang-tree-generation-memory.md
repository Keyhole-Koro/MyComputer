# MyLang メモリモデル 別案：木と世代

**Status:** 不採用（2026-11-05）。代償（CPU の変更、触るたびの照合、個別の削除）が大きい。
代わりに `mylang-values.md`（値だけのモデル）を採った。

**Scope:** rc・gc・所有権と借用のどれにも頼らない、メモリの扱いの案。
`docs/design/mylang-memory-model.md`（rc と所有権を切り替える案）の代わりになる。

この文書は「親子＋世代」と呼んで議論した案を詰めたもの。まだ採用は決まっていない。
採用するかは、§11 の試作で書き味と速さを rc の案と比べてから決める。

---

## 1. 一言で

- **寿命は親が決める。** オブジェクトは必ず親を持ち、プロセスのメモリは1本の木になる。
  親を消すと、子孫もまとめて消える。
- **安全は世代が守る。** オブジェクトに触るたびに、まだ生きているかを CPU が照らし合わせる。
  消したものに触ると、壊れる前に必ずその場で止まる。
- **値はコピーする。** 文字列や `Vec` も、代入するとまるごとコピーして共有しない。

参照の数は数えない（rc ではない）。生きているものを探して回収しない（gc ではない）。
借用中の書き換えを禁じる規則や move の規則もない（所有権と借用ではない）。

## 2. 書き方

```c
object Window {
    Text<32> title;
    Vec<Node> nodes;           // ハンドルの並び。寿命とは関係ない
};

object Node {
    u16 id;
    String text;               // 値。中のバッファはこの Node の子
    Option<Node> next;         // ほかのオブジェクトへのハンドル。輪になってもよい
};

Window win = new(root) Window { title: "Files" };   // root（プロセスの根）の子
Node item = new(win) Node { id: 1, text: "a.txt" };  // win の子
win.nodes.push(item);          // ハンドルはどこに置いてもいい（数えない）
g_focus = Some(item);          // グローバルにも置ける

item.text = "b.txt";           // 古いバッファは消え、新しいバッファが item の子になる

delete win;                    // win と、その子孫（item とそのバッファ）が消える

if (alive(item)) { ... }       // 生きているかは、止まらずに調べられる（ここでは偽）
item.id;                       // trap：消したものに触った（必ずここで止まる）
```

一時的なオブジェクトは、親を書かずに作る。今のブロックが親になり、ブロックを出ると消える。

```c
Parser p = new Parser { src: text };   // このブロックの子
...                                    // ブロックを出ると消える（return・break・? も同じ）
```

## 3. 規則

### オブジェクト

**規則 1（object）** `struct` で宣言した型は値、`object` で宣言した型はオブジェクトになる。
object 型の変数は、オブジェクトを指す**ハンドル**（1語）を持つ。

**規則 2（new）** `new(親) T { フィールド: 値, ... }` はオブジェクトを作り、ハンドルを返す。
親はオブジェクト（プロセスの根は `root`）。`new T { ... }` と親を省くと、今のブロックが親に
なる。省いたフィールドはゼロになる。確保に失敗すると trap する。失敗を扱いたい所では
`try_new` を使い、`Option<T>` を受け取る。

**規則 3（delete）** `delete x` は x と、その子孫をすべて消す。順番は、x の `drop` →
子（作った逆順に、同じ規則で）→ x のメモリ。ブロックが親のオブジェクトは、ブロックを出る
ときに同じ規則で消える。

**規則 4（adopt）** `adopt(新しい親, x)` は x の親を変える（子孫ごと移る）。x の子孫を
新しい親にしようとすると trap する。「このブロックの中で作ったが、うまくいったら残す」は
これで書く（今のガードの `keep()` に当たる）。

**規則 5（ハンドル）** ハンドルは自由にコピー・保存・比較できる。数えないので、何本あっても、
輪になってもよい。`a == b` は同じオブジェクトかどうか。ハンドルは null にならない。無いことが
ある所は `Option<T>` にする（1語に収まり、None は 0）。ハンドルにはゼロ値がないので、
object 型の変数・フィールドは必ず初期化する。

**規則 6（照合）** ハンドルを通してオブジェクトに触るたびに、そのオブジェクトが生きているかを
照らし合わせる。消えていれば trap する。`alive(x)` は止まらずに真偽を返す。

**規則 7（drop）** object は `drop` を持てる。delete のときに1回だけ呼ばれる。ファイルや
ウィンドウのような資源は object にして、drop で閉じる。

### 値

**規則 8（値のコピー）** 値（struct、`Text<N>`、`String`、`Vec<T>`、`HashMap<K, V>`）は、
代入・値渡し・return でまるごとコピーされる。共有はしない。

**規則 9（値のバッファ）** 値が中に持つバッファは、その値を置いている場所の子になる。場所が
オブジェクトのフィールドならそのオブジェクト、ローカル変数ならそのブロック、グローバルなら
プロセスの根。上書きすると古いバッファは消え、場所が消えればバッファも消える。値に `drop` は
書けない。

**規則 10（ゼロ値）** 変数・フィールド・配列の要素は、初期化しなければゼロで始まる。`Option`
は None。ハンドルは例外（規則 5）。

### 参照

**規則 11（ref）** `&場所` は参照 `ref T` を作る。参照は、関数の引数・ローカル変数・戻り値に
だけ置ける。フィールド・グローバル・オブジェクト・閉じ込める関数値には置けない。返せるのは、
引数の参照から作ったものだけ。ヒープの中を指す参照は、触るたびに照合する（規則 6）。

参照の置き場所を絞るのは、ローカル変数を指す参照が関数の外へ出ないようにするためだけ。
今の借用のような「借りている間は書き換えられない」規則はない。借りている間に元が消えたり
作り直されたりしても、ヒープの中なら照合で止まり、ローカル変数ならまだ生きているので、
メモリは壊れない。

### 実行時の検査

**規則 12（範囲）** 配列の添字、参照やハンドルで触る位置は、範囲を検査する。外なら trap。

**規則 13（trap）** trap ではプログラムが止まり、r1 に `0x1BAD00 | 種類` が入る。

| 種類 | 意味 |
| --- | --- |
| `0x01` | 配列の添字が範囲外（実装済み） |
| `0x02` | 消えたオブジェクトに触った |
| `0x03` | オブジェクトの外に触った |
| `0x04` | 確保の失敗 |

### unsafe、スレッド、割り込み

**規則 14（unsafe）** 生ポインタ `T*` は unsafe なファイル（`.unsafe.mln`）だけで使える。
今の `T*` の意味は変えない。

**規則 15（スレッド）** 木を変える操作（new・delete・adopt）は、プロセスの中で1つずつ行う。
照合と読み書きは1命令なので、CPU が1つのうちは、間に別のスレッドの delete が入ることはない。

**規則 16（割り込み）** 割り込みの中では new しない。割り込みの中の delete は、割り込みを
抜けてから行う。

## 4. なぜ安全か

安全なコードがメモリに触る道は、ローカル変数、グローバル、ハンドル、参照の4つしかない
（生ポインタは unsafe だけ）。

1. **ハンドルと、ヒープを指す参照。** 触るたびに、ハンドルが表の今の値と一致するか（生きて
   いるか）と、位置がオブジェクトの中か（範囲）を照らし合わせる。消したオブジェクトの場所が
   別のオブジェクトに使われても、世代が違うので古いハンドルでは触れない。
2. **ローカル変数を指す参照。** 関数の外に出られない（規則 11）ので、指している変数は必ず
   生きている。
3. **型の取り違え。** 生きているオブジェクトにしか触れず、ハンドルは安全なコードからは作れ
   ない（整数からハンドルへの変換はない）。
4. **初期化されていないメモリ。** すべてゼロから始まる（規則 10）。
5. **スレッドと割り込み。** 照合と読み書きが1つの命令なので、その間に消されることはない。
   木の操作は1つずつ行う。

消し忘れは漏れになるが、メモリを壊さない。漏れは、木を眺めれば見つかる（§6）。

## 5. 実装

### 5.1 オブジェクト表

プロセスごとに1つ、カーネルにも1つ持つ。1行は16バイト。

| 語 | 中身 |
| --- | --- |
| 0 | オブジェクトのアドレス |
| 1 | 今のハンドルの値（空きなら 0） |
| 2 | オブジェクトの大きさ |
| 3 | 親の番号 |

ハンドルは32ビットで、上の12ビットが世代、下の20ビットが表の番号。番号 0 は使わない
（None に当てる）。delete すると行の世代を1増やし、行を空きに戻す。世代が一周する行は二度と
使わない。捨てるのは表の16バイトだけで、オブジェクトのメモリは再利用できる。番号は約100万
なので、1プロセスに100万個まで置ける。

子の並び（最初の子、次の兄弟）は、オブジェクトの前に置く見えない8バイトの頭に持つ。

### 5.2 CPU の命令

照合を CPU の命令に入れる。今の命令セットはシフトが1ビットずつで、load にオフセットもない
ので、ソフトウェアで照合すると1回に約15命令かかる。命令にすれば1命令で済む。

| 命令 | 動き |
| --- | --- |
| `ldh rD, rH, imm` | ハンドル rH のオブジェクトの位置 imm から1語読む |
| `sth rS, rH, imm` | 同じ場所へ1語書く |
| `ldhb` / `sthb` | 1バイト版 |
| `ldhx rD, rH, rO` | 位置をレジスタで渡す版（配列、参照） |
| `hchk rH` | 生きていれば Z フラグを立てる（`alive`） |
| `hbase rD, rH` | 照合して、オブジェクトのアドレスを返す（unsafe の実行時ライブラリ用） |

どの命令も、表の行を読み、ハンドルの一致と位置の範囲を確かめてから読み書きする。表の場所は
入出力レジスタで渡し、カーネルが切り替えのときに書き換える（ページ表と同じ扱い）。

内部ではメモリを3〜4回読む。エミュレータでは問題にならない。Verilog の CPU では状態が
いくつか増える。直前に使ったハンドルの行を1つ覚えておけば、同じオブジェクトを続けて触る
ときは表を読まずに済む。

### 5.3 実行時ライブラリ（unsafe）

- サイズ別のページから割り当てるアロケータ。
- 表の空き行のリスト、new・delete・adopt、木のロック。
- 木を書き出す機能（デバッグ用）。型ごとの数、親ごとの子、根からの道。
- `hbase` で得たアドレスは照合を通らないので、使う間は木のロックを持つ（その間は消されない）。

### 5.4 コンパイラ

- 足すもの: `object`、`new` / `new(親)` / `try_new`、`delete`、`adopt`、`alive`、`ref T`。
  ハンドルを通した読み書きを `ldh` / `sth` に。値のコピー（深いコピー）の処理と、バッファの
  親の付け替え。最後の使用は、コピーせずに親を付け替えるだけにする。
- 消せるもの: move の検査、持ち主フラグ、値の `drop`、借用の衝突の検査（「借りている間は
  書き換えられない」）。借用を置ける場所の検査（`parser_borrow_positions.c`）は、規則 11 の
  ためにそのまま使える。
- 予約語: `object`・`adopt`・`alive` は今のコードで識別子として使われていない。`delete` は
  Files アプリのメソッド名に1つある（`void (Files *f) delete(i32 id)`）。

## 6. 見渡し

プロセスのメモリ全体が1本の木なので、DOM インスペクタと同じように眺められる。

```
app (Files)
├─ Window "Files"          128 B
│  ├─ Node #1 "a.txt"      128 B
│  │  └─ String buffer      16 B
│  └─ Node #2 ...
└─ Cache                    64 B
```

漏れは「長生きの親の下に、もう要らない子がたまっている」形で見える。

## 7. コスト

| 項目 | 見積もり |
| --- | --- |
| オブジェクト1つのメモリ | 表 16 B ＋ 頭 8 B。DOM のノード（104 B）なら約 23% 増える |
| ハンドルで触る | 1命令（CPU の命令を足した場合）。今の `addis` ＋ `load` の組より短い |
| ハンドルのコピー | 0（数えない） |
| new / delete | 実行時ライブラリの呼び出し。1つ数十命令 |
| 値のコピー | まるごと。最後の使用は付け替えだけ。大きい値は `ref` で渡す |

rc の案と比べると、ポインタをコピーするたびの増減（3〜5命令）がなくなり、代わりに触るたびの
照合が入る。照合は命令に入れれば増えない。

## 8. rc の案との比較

| | rc ＋所有権の案 | 木と世代 |
| --- | --- | --- |
| 解放 | 参照数が 0 になったとき | 親か自分を delete したとき |
| 輪 | weak で切る | 何もしなくていい |
| 書き方の規則 | モード、move、借用の規則 | 親を決める、参照の置き場所 |
| 間違えたとき | 輪の漏れ、借用はコンパイルエラー | 消したものに触ると実行時に止まる。消し忘れは漏れ |
| 値 | 共有してコピーオンライト | まるごとコピー |
| 実行時のコスト | コピーごとの増減 | 触るたびの照合（命令に入れれば 0） |
| CPU の変更 | 要らない（あれば速い） | ほぼ必須 |
| 仕様の大きさ | 規則 40 前後 | 規則 16 |

## 9. 今のコードからの移行

DOM のノードの作成（`dom.mln` の `create_node`）は、`heap.alloc` の失敗処理、`Node *` への
キャスト、約30行のゼロ埋めが、次の1文になる。

```c
Node n = new(owner_root(g_current_owner)) Node { id: id, kind: kind, name: name,
                                                 owner: g_current_owner };
g_node_table[id] = Some(n);
```

`owner_root` は、アプリごとに持つ根のオブジェクトを返す。アプリが終わればその根を消すだけで、
そのアプリのノードがすべて消える。

- ノードの番号（`u16 id`）は、アプリとの通信で使うので残し、番号からハンドルへの表にする。
  親・子・兄弟の `u16` はハンドル（`Option<Node>`）になる。
- カーネルのガード（`ProcessSlot`・`AddressSpace`・`HeapBlock`）は、ブロックの子として作り、
  成功したら `adopt` で残す形になる。
- `heap.alloc` / `heap.free` は `new` / `delete` に、`char *` の文字列は `String` か `Text<N>` に
  置き換える。
- 生ポインタの操作は、今と同じく `.unsafe.mln` に寄せる（MLC-023）。

採用した場合、`mylang-memory-model.md` の rc・モード・共有・借用の衝突の規則は書き直しになる。
範囲検査・ゼロ初期化・網羅性・借用を置ける場所の規則は、そのまま使える。MLC-024 の借用の
衝突の検査は、要らなくなる。

## 10. 未決事項

- **戻り値。** ブロックの子をそのまま return すると、呼び出し元で消えている。作る関数は親を
  引数で受け取る形にし、ブロックの子を return したらコンパイラが警告する案。
- **大きな値のコピー。** 共有したい大きなデータは object にする。どこまで目安を決めるか。
- **小さい文字列。** `String` ごとに表の1行と頭を使うので、短い文字列は中に直接持つ工夫が要る。
- **スレッド。** 木のロックの粒度。
- **CPU。** Verilog に入れる手間と、直前のハンドルを覚える仕組みの効き目。
- **書き方。** `object` / `new(親)` / `ref T` の綴り、親を省いた `new` を許すか。

## 11. 試作の計画

1. エミュレータとアセンブラに、オブジェクト表と §5.2 の命令、trap `0x1BAD02` / `0x1BAD03` を
   足す。
2. 実行時ライブラリ（unsafe な MyLang）に、表、new・delete・adopt を書く。最初は1スレッド。
3. コンパイラに最小限を足す。`object`、`new(親)`、`delete`、`alive`、フィールドの読み書き。
4. 止まるまで動く比較用のプログラムで、木を作る・たどる・消す処理の命令数を比べる。今の
   生ポインタ、rc（ソフトウェアの増減）、木と世代の3つ。
5. DOM の一部を書き直して、書き味を見る。
